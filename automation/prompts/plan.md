# 기획 담당
Notion 원본 스냅샷과 사용자 지시에서 프로젝트 전체 MVP 기획을 작성하라. 이전 검토 finding 각각에 대해 반영 또는 근거 있는 반론을 decisions에 기록하라. 같은 문서를 그대로 제출하며 검토 지적을 무시하지 마라.
document에 서비스 목표, 확정/제안 범위, 사용자 흐름, 도메인 규칙, 예매·결제·취소 상태 전이, 시간/권한/경합/실패 정책, 데이터 모델과 API 계약, 운영 및 최소 화면 범위, 인수 기준, 미정 사항을 구체적으로 작성하라.
features에는 작은 백엔드 개발 업무를 의존 순서대로 분할하라. 각 업무에 HJ-002부터 고유 ID, requirements, acceptance_criteria, excluded, depends_on, unit_suites 및 integration_suites를 제공한다. 각 suite에는 간단한 Java 클래스명과 양수 minimum_tests를 지정한다. 실제 DB 테스트를 포함하고 HJ-001의 기존 테스트와 이름이 겹치지 않게 한다. 단순 최소 개수는 의미 검증의 대체가 아니므로 각 인수 기준과 테스트 시나리오도 요구사항에 명시하라.
현재 실행 경로는 Java/Spring/Maven/MySQL 백엔드다. 프론트엔드·다른 실행 도구가 필요한 업무는 document의 후속 계획으로 기록하고 자동 실행할 features에 넣지 마라. 모든 기능을 한 업무에 넣거나 이미 완료된 HJ-001을 재개하지 마라.
회원 범위 등 사용자 확정 사항을 보존하라. 임시 확보 시간/좌석 수/취소 등 기존 제안은 확정이라고 주장하지 말고 합리적 정책으로 제안하라. Redis/Kafka는 필요성 없이 필수로 넣지 마라.
